# Project Context Maintainer

维护一份能让后续 AI 会话迅速理解项目、且不必全量重新探索仓库的 `AGENTS.md`。文档重点是项目约定和决策：代码风格、设计规范、架构边界、运行方式、重要业务规则、已知限制和协作流程；不要把它写成源码或 README 的重复副本。

## 何时介入

- 当用户新建项目、讨论新项目的需求或架构时，主动把建立 `AGENTS.md` 纳入启动流程。
- 当用户要求创建、补充或更新项目介绍、AI 上下文、项目约定、设计规范或编码规范时使用。
- 在普通实现工作中，只有改动实质影响已记录的架构、约定、依赖、运行命令、目录职责或业务规则时，才依照该项目选定的维护策略处理；不要为微小实现细节制造噪声。

## 首次用于一个项目

1. 确认项目根目录。先检查根目录是否存在 `AGENTS.md`。
2. 若文件已存在，完整读取并向用户列出文件路径与当前内容；不要在得到明确决定前改写它。请用户决定保留、合并、替换、另存或采取其他处理。执行前遵循其选择。
3. 若文件不存在，说明将创建它。
4. 每个项目首次使用时，询问用户选择后续维护策略，并把原意清晰写入 `AGENTS.md`：
   - 自动更新：相关实质改动完成后直接同步文档，并在交付时说明；
   - 确认后更新：先展示拟改内容，用户确认后再写入；
   - 仅提醒：发现应同步的改动时提醒用户，不自行写入。
5. 递归阅读项目中的文本文件，结合用户对项目目标和要求的描述生成初稿。读取应覆盖源代码、配置、文档、测试和构建脚本，而不是只看文件名或抽样。跳过二进制文件、依赖缓存/包目录、构建产物、版本控制元数据和环境变量/密钥文件；这些文件如有必要只记录其存在及用途，绝不转录敏感值。
6. 先向用户展示完整 `AGENTS.md` 草稿，征求确认。只有用户明确确认后，才创建或写入文件。

项目规模过大而无法在一次上下文中完整阅读时，如实说明限制，分批读取全部可读文本文件并给出覆盖范围；不要假装已经完成全量扫描。

## 文档内容

根据项目实际情况选取内容，优先准确、可执行、可维护的信息。通常包括：

- 项目目的、用户和主要能力；
- 技术栈、关键入口、目录职责及重要数据/调用流；
- 本地运行、测试、构建与发布相关命令；
- 代码风格、命名、错误处理、测试、依赖和安全约定；
- 视觉/交互或领域设计规范，以及明确禁止的做法；
- 架构边界、外部服务、重要业务规则、已知限制与未决事项；
- `AGENTS.md` 的维护策略，以及何种变更必须同步该文档。

把事实、用户明确选择和合理推断区分开。对无法从文件或用户描述确认的内容，标为“待确认”，不要杜撰。避免记录瞬时进度、密钥、个人信息、逐行代码解释、复制的大段配置或很快过期的实现细节。

## 后续维护

每次完成实质改动后，先对照 `AGENTS.md` 中的维护策略和实际变更范围判断是否需要同步。更新时只调整受影响的段落，保留用户已有内容和结构；如已有内容与当前事实冲突，指出冲突而不是静默删除用户意图。

对于“确认后更新”模式，展示准确的拟改文本或清楚的差异，再等待确认。对于“自动更新”模式，只有在文档归属和改动含义清晰时才直接更新；遇到冲突、内容来源不明或可能覆盖人工决策时，暂停并询问。对于“仅提醒”模式，只说明建议更新的具体段落与原因。

## 写作要求

使用项目已有的语言与术语；若项目没有既有约定，使用用户偏好的语言。结构应方便后续 Agent 快速定位信息，可使用简洁标题和列表。优先写“为什么及边界条件”，而不是显而易见的操作说明。除非用户要求，不改动 `AGENTS.md` 以外的项目文件。
