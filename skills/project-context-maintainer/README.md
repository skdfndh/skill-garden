# project-context-maintainer

> 在项目根目录创建并维护一份 `AGENTS.md`——让后续的 AI 会话不必每次从零重新探索你的仓库。

## 它解决什么问题

每次开一个新的 AI 会话，你都要重新解释一遍：这个项目的架构边界在哪、哪些约定不能破、测试怎么跑、上次为什么否掉了某个方案。说一遍不累，说二十遍就很累，而且每次说的还可能不一致。

`AGENTS.md` 是解决这个问题的标准做法：把**项目约定与决策**写成一份放在仓库根目录的文档，AI 每次开工前先读它。

但这个文件很容易写成两种没用的东西——源码的复述，或者 README 的副本。这个技能的价值在于它知道该写什么、不该写什么。

## 它产出什么

一个 `AGENTS.md`，内容聚焦在**能改变 AI 决策**的信息：

- `AGENTS.md` 自身的维护策略（后续什么时候该更新它）
- 项目目的、用户与主要能力
- 技术栈、关键入口、目录职责、重要数据流
- 本地运行、测试、构建、发布命令
- 代码风格、命名、错误处理、测试、依赖与安全约定
- 架构边界、外部服务、重要业务规则、已知限制、未决事项
- 明确禁止的做法

**刻意不写**：瞬时进度、密钥、个人信息、逐行代码解释、大段配置复制、很快过期的实现细节。

## 触发场景

- 新建项目，或开始讨论一个新项目的需求与架构
- 要求创建/补充项目介绍、AI 上下文、编码规范、设计规范
- 项目发生实质变更，需要同步已有文档

**不适用于**：只是读写普通 `README.md` 的请求。

## 使用示例

```text
帮这个项目建一份 AGENTS.md，我接下来要在这个仓库里做不少改动。
```

```text
我们刚把认证从 session 换成了 JWT，更新一下 AGENTS.md 里相关的约定。
```

```text
读一下这个仓库，梳理出给 AI 用的项目上下文。
```

## 一个刻意的设计：维护策略前置

技能要求**首次使用时先问用户选哪种维护策略**，并把选择写进 `AGENTS.md`：

| 策略 | 行为 |
| --- | --- |
| 自动更新 | 相关实质改动完成后直接同步文档，交付时说明 |
| 确认后更新 | 先展示拟改内容，用户确认后再写入 |
| 仅提醒 | 发现应同步的改动时提醒，不自行写入 |

原因是：文档失效的主要机制不是"没人写"，而是"没人知道该谁写、什么时候写"。把策略显式写下来，后续会话才知道该怎么处理。
