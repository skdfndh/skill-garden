# skill-optimizer

> 审查并改写已有的 Agent Skill——提升触发准确性、指令可执行性、边界清晰度与渐进披露。

## 它解决什么问题

写 Skill 容易犯两类错，而且方向相反：

**写太少**——只写"帮我处理 X"，Agent 拿到后不知道边界在哪、什么情况该停下来问、输出该长什么样，每次执行结果都不一样。

**写太多**——把所有踩过的坑都固化成硬规则，堆成一长串 `ALWAYS`/`NEVER`。结果入口文件膨胀到读不完，真正重要的约束反而被淹没，而且规则之间开始互相矛盾。

这个技能的作用是在这两极之间找到位置：**只保留真正能改变 Agent 决策的内容**。

## 四个审查维度

| 维度 | 检查什么 |
| --- | --- |
| **触发与边界** | `name`/目录名/frontmatter 是否一致有效；`description` 是否同时说清能力、触发场景与排除范围；哪些操作需要用户授权 |
| **指令质量** | 找出重复、矛盾、无法执行、过度绝对、或只是在复述平台通用规则的内容；关键限制与停止条件是否足够 |
| **信息结构** | 入口是否只保留每次都需要的规则；`references/`/`scripts/`/`assets/` 是否都有真实用途与可发现入口；是否在复制外部工具的完整手册 |
| **可验证性** | 链接、相对路径、命令、文件名是否与当前目录一致；有校验器时是否实际运行过 |

## 一个刻意的边界：默认只审查

技能默认**不修改任何文件**。只有用户明确说"修改""改写""直接优化"时才写入，而且：

- 改动会触及**触发范围、外部副作用、目录结构或用户流程**时，先展示方案再等确认
- 保留用户已选择的语言、权限边界、依赖与工作流——**不把本技能的偏好当成目标 Skill 的规则**
- 写入时采用最小改动：保留正确内容，只改已确认的问题
- 不覆盖不属于当前请求的未提交修改

最后一条在实践中很重要：你手上可能有别的活儿没提交，一个"帮我优化下 Skill"的请求不该把它们卷进去。

## 它的输出长什么样

审查结果按固定顺序给出，避免只给抽象评价：

```
1. 审查范围    读了哪些文件，哪些关联资源未读及原因
2. 发现的问题  按「阻塞 / 重要 / 改进」排序，每项给证据、影响与建议
3. 改写方案    列出会改动的文件、关键差异及取舍
4. 验证结果    实际运行的命令、结果，以及未覆盖的部分
```

**没有问题时会明确说没有问题**，不为凑改动而重写——这是审查类技能最容易失守的地方。

## 触发场景

- "帮我看看这个 Skill 写得对不对"
- "这个 Skill 老是不触发，优化一下 description"
- "SKILL.md 太长了，帮我精简"
- "审查一下我这些 Skill 的结构"

**不适用于**：从零创建 Skill（那是 `create-skill` / `skill-creator` 的活），或只是执行某个 Skill。

## 使用示例

```text
审查一下 skills/repo-privacy-hardening，看看 description 的触发范围有没有问题。
```

```text
我这个 SKILL.md 有 800 行，帮我看看哪些内容该拆到 references/ 去。
```

## 和同类技能的分工

| 场景 | 用哪个 |
| --- | --- |
| 从零创建一个 Skill | `create-skill` / `skill-creator` |
| 审查并改写已有 Skill | **本技能** |
| 执行某个具体 Skill | 直接用那个 Skill |

## 安装

```bash
cp -r skills/skill-optimizer ~/.claude/skills/     # Claude Code
cp -r skills/skill-optimizer ~/.agents/skills/     # Codex 与 DSH
```
