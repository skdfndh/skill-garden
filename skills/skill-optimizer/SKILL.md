# Skill Optimizer

把已有 Skill 改得更容易被正确触发、更容易遵循，并且只保留真正能改变 Agent 决策的内容。优化不是把说明写得更长，也不是把所有经验固化成硬规则。

## 审查范围

1. 先确认目标 Skill 目录与用户期望。完整阅读 `SKILL.md`；只读取其明确链接、当前任务相关的 references、scripts 或 assets。改动关联资源前，先阅读其内容和调用位置。
2. 了解目标仓库的本地约定、未提交改动和已有验证方式。保留用户已经选择的语言、权限边界、依赖和工作流；不要把本 Skill 的偏好当成目标 Skill 的规则。
3. 默认只审查。用户明确要求“修改”“改写”“直接优化”时，才写入文件；如果改动会改变触发范围、外部副作用、目录结构或用户流程，先展示方案并等待确认。

## 审查维度

### 触发与边界

- `name`、目录名和 YAML frontmatter 是否一致且有效。
- `description` 是否用简洁语言同时说明能力、典型触发场景和必要的排除范围。不要把相邻但不同的任务一并吸引进来。
- 正文是否明确哪些操作需要用户授权，哪些请求应转交给其他 Skill 或普通工作流。

### 指令质量

- 找出重复、矛盾、无法执行、过度绝对或只是在复述通用平台规则的内容。
- 检查关键限制、输入、输出和停止条件是否足以让 Agent 在真实任务中作出一致判断。
- 保留有具体风险、历史约束或领域依据的规则；不凭想象补充限制，也不为单个偶发案例堆砌流程。

### 信息结构

- 入口只保留每次执行都需要的共同规则。只有在特定模式才需要的详细步骤、格式或背景资料，才放到可明确路由的 `references/`。
- 每个 scripts、references 或 assets 文件都必须有真实用途、可发现入口和正确路径；没有明确收益时，不新增目录、模板或示例。
- 避免复制外部工具的完整手册。引用资源时说明何时读取，而不是要求一次性加载全部内容。

### 可验证性

- 检查 Markdown 链接、相对路径、命令、文件名和前置条件是否与当前目录一致。
- 有现成校验器或脚本时运行与改动相关的最小验证；不要把“文本更通顺”宣称为行为已验证。
- 区分可自动验证的结构问题与需要人工判断的提示词质量，并如实说明两者的覆盖范围。

## 输出与改写

审查结果按以下顺序给出，避免只给抽象评价：

1. **审查范围**：读了哪些文件，哪些关联资源未读及原因。
2. **发现的问题**：按“阻塞、重要、改进”排序；每项说明证据、影响和建议。
3. **改写方案**：列出会改动的文件、关键差异及其取舍。没有问题时明确说明，不为凑改动而重写。
4. **验证结果**：列出实际运行的命令、结果和未覆盖部分。

写入时采用最小改动：先读取原文件，再保留正确内容并只改已确认的问题。不要覆盖不属于当前请求的未提交修改，不要新增依赖或执行外部变更。完成后重新检查 frontmatter、链接与相关命令，并报告仍需要用户决定的事项。
