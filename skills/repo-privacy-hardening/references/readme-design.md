# README 设计：从"信息齐全"到"让人想用"

第 6 步的 README 专项。`references/github-layout.md` 讲的是**结构正确性**（该有哪些章节），这一份讲**说服力与观感**（同样齐全，为什么有的仓库 300 star 有的无人问津）。

判断标准只有一条：**陌生人滚过前两屏，会不会想点 Star 或 clone 下来试。**

## 一、先想清楚给谁看

README 是五类读者的公共入口，他们关心的东西完全不同：

| 读者 | 停留时长 | 他找什么 | 对应位置 |
| --- | --- | --- | --- |
| 路过的开发者 | ~5 秒 | 这是什么、跟我有关吗 | 标题 + 一句话 + 截图 |
| 想用的人 | ~2 分钟 | 怎么跑起来、要配什么 | 快速开始 + 配置 |
| 想贡献的人 | ~5 分钟 | 代码结构、怎么验证改动 | 开发 + CONTRIBUTING |
| 想评估的人 | ~1 分钟 | 靠谱吗、有人在用吗、什么许可 | 徽章 + 许可证 + 活跃度 |
| 未来的你自己 | 半年后 | 当时为什么这么设计 | 设计决策段落 |

**写之前先确定主要读者是谁。** 一个给自己用的脚本和一个给别人用的库，README 的写法完全不同：前者可以只有用法，后者必须把边界条件、兼容性、迁移方式说清楚。

## 二、排版：Markdown 的视觉层级

Markdown 能用的视觉手段比 CSS 少得多，所以每一样都要用准。

### 标题层级：不要跳级

`#` 只出现一次（项目名），`##` 是主要章节，`###` 只在章节内部真的需要细分时用。**跳级（`#` 直接到 `###`）会在 GitHub 的目录树上产生断层**，也会让右侧 TOC 显示得很奇怪。

标题写"读者的问题"，不写"文档的栏目"：

| 别写 | 改写成 |
| --- | --- |
| 简介 | （不需要，第一段就是简介） |
| 功能特性 | 能做什么 |
| 环境要求 | 开始前你需要什么 |
| 使用方法 | 怎么用 |
| 注意事项 | 常见问题 |

### 首屏：前 15 行决定一切

GitHub 的 README 在桌面端大约显示 15 行就会遇到"折叠线"。这 15 行里必须出现：

1. **项目名**（一句话标题）
2. **一句话说清是什么、给谁用**
3. **一张截图或一段终端输出**（如果有界面或 CLI）
4. **徽章**（可选，但许可证和构建状态的徽章能立刻建立可信度）

反面例子是那种开头写三行免责声明、五行背景介绍、然后才说这个项目是干什么的 README。

### 一句话怎么写

**公式**：`[给谁用] + [具体能做什么] + [关键差异点]`

- ❌ "本项目是一个基于 React 和 TypeScript 的现代化前端应用"——同义反复，读者还是不知道它干什么
- ❌ "让效率提升 10 倍"——空洞的营销话术
- ✅ "把散落在微信里的聚餐提议，整理成一张可以投票的地图"——具体、有画面
- ✅ "扫描项目里的密钥和个人信息，然后帮你把仓库改造成能公开的样子"——读者立刻知道该不该继续往下看

**检验方法**：把这句话单独发给一个不了解项目的同事，问他"这东西是干嘛的"。他答得上来就是写对了。

### 代码块：标语言、给可复制的东西

- 每个代码块都标语言（```bash / ```python / ```json）——GitHub 会据此高亮，不标就是一片灰
- **命令要能直接复制粘贴运行**，不要写 `<你的路径>` 这类需要读者自己替换的东西（除非真的必须）
- 终端输出用独立代码块，不要和命令混在一起
- 一个代码块只做一件事：装依赖、跑测试、启动服务各一块

### 表格用来对比，不用来堆信息

表格适合"同一组属性在多个选项间的对比"（支持哪些平台、各配置项的含义）。**不要**把一整段说明硬塞进两列表格——那不如直接写段落。

```markdown
| 平台 | 最低版本 | 备注 |
| --- | --- | --- |
| Windows | 10 (1809+) | 需要 .NET Framework 4.7.2 |
| macOS | 12+ | Apple Silicon 原生支持 |
```

### 折叠块：把长内容藏起来但保留可查性

安装日志、完整的配置项列表、FAQ 这类"不是所有人都要看，但有人会查"的内容，用 `<details>` 折叠：

```markdown
<details>
<summary>全部 37 个配置项</summary>

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
...

</details>
```

**不要**把关键信息（安装步骤、许可证）折进折叠块——折叠 = 暗示"不重要"。

## 三、视觉细节：不靠 CSS 也能提升观感

### 徽章：2-4 个就够，多了像广告

最有信息量的几个：

```markdown
![License](https://img.shields.io/badge/license-MIT-blue.svg)
![Build](https://github.com/<owner>/<repo>/actions/workflows/ci.yml/badge.svg)
![Version](https://img.shields.io/github/v/release/<owner>/<repo>)
```

`shields.io` 是通用来源。**别放"PRs Welcome""Made with ❤️"这类零信息量的徽章**——它们占位置但不回答任何问题。徽章要按重要性排，把许可证放最前。

### 截图与动图：一张好图胜过三段文字

- **有界面就必须放截图。** 这是投入产出比最高的一项
- 有交互动效的项目，用 GIF 或短视频（控制在 5MB 以内，GitHub 有文件大小限制）
- 截图放在仓库内的 `docs/images/` 并在 README 里用相对路径引用——用外链会失效
- 终端类项目可以贴一张真实的运行输出截图，比描述更直观
- **不要放设计稿或概念图**：读者看到实物和图片不符会立刻失去信任

### 目录（TOC）：只在超过 5 屏时才加

GitHub 右侧本身有目录。README 长到需要滚动多屏时，可以在开头加一个手写 TOC；**短 README 加 TOC 是纯粹的噪音**。

### 一致的空行与分隔

- 标题前后各留一个空行
- 列表前后各留一个空行（否则 GitHub 可能不渲染成列表）
- 章节之间用 `---` 分隔线要谨慎——用多了会把页面切得很碎

## 四、说服力：让人相信这东西能用

### 信任信号要具体

| 空洞 | 具体 |
| --- | --- |
| "性能优异" | "处理 10 万行日志约 1.2 秒（M1 MacBook Air）" |
| "广泛使用" | "已被 3 个内部项目使用" |
| "易于扩展" | 给一个 20 行的扩展示例 |
| "经过充分测试" | "测试覆盖率 87%"，或贴 CI 徽章 |

**没有数据就别写形容词。** 空话不会加分，只会让读者跳过整段。

### 主动说清边界

**明确写出"不做什么"比罗列"能做什么"更能建立信任。**

```markdown
## 不适用场景

- 需要多用户协作的场景（本项目是单机工具，没有账号系统）
- 超过 10 万条记录（当前实现是全量加载到内存）
- Windows 7 及更早版本
```

主动暴露限制，读者会觉得作者诚实；藏着不说，读者踩坑后会留下差评。

### 一个完整可跑的例子

比十行功能描述更有用的，是一个**从零到跑通**的完整例子。结构是：

````markdown
## 快速开始

```bash
git clone https://github.com/<owner>/<repo>.git
cd <repo>
npm install
cp .env.example .env      # 然后填入你的 API Key
npm run dev
```

打开 http://localhost:3000，应该看到：
（此处贴一张运行后的截图）
````

关键在于**最后那句"应该看到什么"**——它让读者能自己判断是否成功了，而不是跑到一半不知道对不对。

## 五、常见错误清单

按出现频率排序，这些是会实际劝退读者的：

| 错误 | 为什么致命 | 改法 |
| --- | --- | --- |
| 克隆地址是 `<仓库地址>` 占位符 | 第一条命令就失败，读者直接关页面 | 换成真实 URL |
| 快速开始的命令跑不通 | 同上，而且更伤信任 | 在干净目录里实测一遍 |
| 许可证声明与实际 LICENSE 不一致 | 法务上说不清，企业用户直接放弃 | 对齐，并在 README 里加许可证章节 |
| README 描述的功能代码里没有 | 一次失望就再也不会回来 | 删掉，或标注"计划中" |
| 只罗列技术栈 | 读者不关心你用了什么，只关心能干什么 | 改写成能力 |
| 通篇没有可复制的命令 | 读者要自己猜怎么用 | 每步都给命令 |
| 链接指向已删除的文件 | 显示 404，显得项目荒废 | 定期跑 `-Mode readme` 检查 |
| 提到的配置文件已被删除 | 文档与代码脱节，最难发现的一类 | 改代码时同步改文档 |
| 中英文混杂且无规则 | 观感混乱 | 选定一种主语言，术语首次出现时给对照 |

倒数第二项值得单独强调：**文档漂移是最隐蔽的 README 缺陷**。代码改对了、文档没跟上，本地看不出来、CI 也不报错，只有读者会撞上。所以 `Scanner.ps1 -Mode readme` 会核对 README 提到的文件是否真实存在——但"README 描述的行为是否还对"，仍然只能靠人比对。

## 六、优化已有 README 的工作流

不要一上来就重写。按这个顺序做，每一步都能独立交付：

1. **跑 `Scanner.ps1 -Mode readme`** 拿到客观问题清单（死链、占位符、许可证不一致、健康分）
2. **修正确性问题**——这些是硬伤，优先级最高，且改起来最快
3. **重写第一句话和快速开始**——投入产出比最高的两处
4. **补截图**——有界面的话，这一步的收益超过后面所有步骤
5. **调整章节顺序**——把读者最关心的往前放，把背景介绍往后挪或删掉
6. **润色视觉细节**——徽章、代码块语言标注、表格、折叠块
7. **加许可证章节**并核对与 LICENSE 文件一致

**每一步改完都值得让用户看一眼。** 一次性重写整个 README 会让人无法判断哪处改动是好是坏。

## 七、不该做的事

- **不要为了凑长度而写。** 一个 CLI 工具的 README 可能 40 行就够了，硬撑到 200 行反而没人读。
- **不要抄别的项目的 README 结构。** 库、应用、工具、教程的结构需求完全不同。
- **不要用"赋能""闭环""抓手"这类词。** 它们不传递任何信息。
- **不要放自动生成的 API 文档。** 那应该是单独的文件或网站。
- **不要在 README 里放密钥示例的真实值。** 示例值一律用占位符——这条与本技能的隐私原则一致。
