# 非文本隐私核查清单

扫描器看不到的地方。这些项**必须由人确认**，因为它们的共同点是"信息是否敏感取决于上下文，而不取决于形态"。

按项目类型取用，不需要每项都问。原则是：只要项目里有对应的东西，就明确问一句，不要把"没报警"当作"没问题"。

## 图片与截图

最容易被忽略，也最容易出事。一张后台截图可能同时暴露内网域名、真实用户名、订单号、金额和浏览器书签栏。

- 界面截图里的账号名、头像、真实姓名、邮箱
- 后台地址栏（内网域名或 IP）、接口路径里的业务 ID
- 表格与列表里的真实数据：订单号、手机号、身份证、金额、客户名称
- 聊天记录截图（微信、钉钉、飞书）——往往含人名与内部讨论
- 图片的 EXIF 元数据：拍摄设备、GPS 坐标、拍摄时间、作者信息
- 二维码与条形码（可能是内网地址或带 token 的登录链接）

处置：重新截图并打码，或用 `exiftool -all= image.jpg` 清除元数据后再入库。**打码要盖死**——半透明马赛克和模糊滤镜可以被还原。

## 数据文件

- `*.csv` / `*.xlsx` / `*.json`：是真实业务数据还是编造的示例？
- `*.db` / `*.sqlite` / `*.sql` 导出：里面的表结构与数据是否含真实用户
- `*.log`：日志里几乎必然含 IP、用户 ID、请求参数，有时还有 token
- 数据集文件：来源是否有再分发许可？很多公开数据集的授权不允许二次分发
- 测试夹具（fixtures）：从生产环境复制来的样本是最常见的泄露源

处置：真实数据替换为合成数据。**不能用打码后的真数据**——手机号打码、姓名缩写仍然属于个人信息，而且样本一多就能被关联还原。

## 文档与注释

- 内部文档的链接（Confluence、Notion、飞书、内网 Wiki）
- 工单号、项目代号、内部系统名
- 注释里残留的临时凭据、临时账号、调试用的后门开关
- `TODO` / `FIXME` 里透露的内部信息："等张三确认后改成真实接口"
- 架构图里画出的内网拓扑、服务器 IP、数据库名

## 二进制与工程文件

扫描器直接跳过这些：

- Office 文档的修订记录与作者字段（`.docx` 属性里含真实姓名）
- PDF 的元数据与批注
- IDE 配置（`.idea/`、`.vscode/`）：本机绝对路径、历史打开记录、数据库连接配置
- 编译产物与调试符号：可能含源码路径与内部函数名
- `.pdb`、`.map` 文件：还原源码结构

## 提交历史与仓库元信息

- 提交作者的姓名与邮箱（公开仓库会永久展示）——不愿公开就用 GitHub 的 noreply 邮箱：`<id>+<username>@users.noreply.github.com`
- 提交信息里提到的内部项目名、工单号、客户名
- 已删除的 tag / branch 名（可能含内部代号）
- 仓库的 description 与 topics 是否也需要脱敏

## 依赖与许可

- 依赖清单里有没有公司内部包（私有 registry 地址本身就是内网信息）
- 引入的第三方代码许可证是否与你要用的 LICENSE 兼容——把 GPL 代码放进 MIT 项目是许可证冲突
- 项目里有没有从别处复制来的代码而没有保留原始版权声明

## 收尾问题

扫描和清单都走完之后，用这两个问题做最后确认，它们能抓到前面所有规则都漏掉的情况：

1. **"如果这段内容明天出现在 Hacker News 上，你会有什么感觉？"** —— 触发对"说不清哪里敏感但就是不想公开"的直觉判断。
2. **"这个仓库里有没有任何东西，是你需要问别人才能决定能不能公开的？"** —— 客户数据、合作方信息、公司内部资料通常属于这一类，需要用户去取得授权，而不是自己判断。
