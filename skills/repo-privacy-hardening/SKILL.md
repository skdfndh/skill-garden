# Repo Privacy Hardening

把一个「只有自己知道里面有什么」的项目，安全地变成可以给陌生人看的公开仓库。

这件事的风险不在技术难度，而在于**不可逆**：一次 `git push` 之后，即使立刻删除文件、立刻重写历史，密钥也已经泄露给了所有抓取 GitHub 新仓库的爬虫和模型训练管线；真实数据一旦公开，就再也收不回来。所以这个技能的重心是「想在动手之前」，而不是「删得快」。

## 三条不可动摇的规则

**报告不是可信文件，它本身就是隐私。** 扫描报告会列出所有问题位置；把它写进仓库目录，等于用一份新文件重演了你要修的问题。报告一律写到被扫描仓库之外（系统临时目录），并可在交付时明确告知用户"这份报告本身别提交"。

**不要把明文敏感值显示给任何人。** 报告里的敏感值一律掩码（`sk-abc1…7f9c`）。原因很实际：报告会被读进 AI 上下文、被贴进聊天窗口、被转发归档——明文出现在其中就是二次泄露，而且泄露得比原文件更彻底（原文件至少还躺在私有仓库里，聊天记录可不一定）。给用户看的摘要里更要克制：说"3 个 AWS 密钥、2 个数据库连接串"，而不是把值抄一遍。

**只提案，不擅自改。** 任何文件修改、git 操作、远端创建，都要先说明"改哪个文件、改成什么、影响什么"，拿到确认再动手。用户说"你看着办"也只授权了低风险项（补 `.gitignore`、写 README），不包含删除文件、重写历史、推送远端。

## 流程

### 第 1 步：侦察

先搞清楚项目是什么，再决定用哪套规则和模板：

- 语言与包管理器（决定 `.gitignore` 模板与 CI 模板）
- 是否已是 git 仓库；若是，`git remote -v` 看有没有远端、`git rev-list --count HEAD` 看提交规模
- 有没有现成的 `.gitignore`、`LICENSE`、`README`
- 项目里有没有明显的数据目录（数据集、导出文件、数据库文件、截图），这些地方往往藏着正则抓不到的真实信息

### 第 2 步：扫描

优先用本技能自带的扫描器，它是确定性的，不受模型状态影响：

```powershell
pwsh -File ./scripts/Scanner.ps1 -Path <项目根> -OutDir <仓库外的目录>
```

| 参数 | 用途 |
| --- | --- |
| `-Mode secrets\|pii\|infra\|hygiene\|readme\|all` | 只查某一类，便于分阶段推进 |
| `-Exclude <目录名...>` | 排除额外目录；依赖目录与构建产物默认已排除 |
| `-All` | 取消每类 200 条的上限 |
| `-Json` | 只输出 JSON，便于脚本消费 |

`-Mode readme` 做的是**正确性**检查，不是存在性检查：死链、未替换的占位符、图片引用失效、README 声称的许可证与仓库里的 LICENSE 是否对得上、克隆地址是不是模板残留，最后给出一个 0-10 的健康分。它抓的都是"本地看着没问题、只有读者会撞上"的缺陷。

退出码 `1` 表示存在 P0 问题，可以直接用它在自动化里卡发布。

扫描器没装 `gitleaks`，用的是自建规则＋香农熵兜底，覆盖常见云厂商与平台凭据。如果用户环境里有 `gitleaks` 或 `trufflehog`，值得额外跑一遍做交叉验证——不同工具的正则侧重点不同，漏报比误报更危险。

扫描器抓不到的东西必须靠人看，扫描结束后主动补这几个问题：

- 仓库里的示例数据、测试夹具、CSV/JSON 导出文件，是不是真实业务数据？
- 截图、录屏、演示文档里有没有真人姓名、聊天记录、后台地址、订单信息？
- 二进制文件（`.xlsx`、`.docx`、`.db`、`.sqlite`）里的内容扫描器读不到，是否需要打开确认？
- 提交历史里的作者姓名与邮箱是否愿意公开？

### 第 3 步：分级报告与提案

把结果整理成 P0/P1/P2 三档呈现给用户，每档给出**具体处置动作**而不只是问题位置：

| 等级 | 判据 | 处置 |
| --- | --- | --- |
| **P0** | 密钥、令牌、私钥、内嵌凭据的连接串、`.env` 等凭据载体 | 阻塞开源；先轮换密钥，再清理文件 |
| **P1** | 手机号、身份证号、邮箱、本机绝对路径、内网 IP 与内部域名、真实业务数据 | 替换为占位符或合成样例 |
| **P2** | 提交作者身份、可能含凭据的通用配置文件、超过 1MB 的已跟踪文件 | 逐项判断，用户决定 |

汇报时按类别聚合（"7 个文件里有 3 个 AWS 密钥"），并明确说出本轮扫描的**覆盖范围与盲区**——扫了哪些目录、跳过了什么、哪些结论需要人确认。不要暗示"没扫出问题就等于干净"。

### 第 4 步：清理（逐项确认后执行）

按 P0 → P1 → P2 顺序推进，每一项拿到确认再动手：

- **移出而非删除**：`.env`、密钥文件、真实数据先移到仓库外或加到 `.gitignore`，再 `git rm --cached`。直接删除会让用户失去本地可用副本。
- **配套改动要一起做**：把硬编码凭据改成读环境变量后，必须同步给 `.env.example`、README 的运行说明、CI 的 secrets 配置。只改代码不改文档，项目就跑不起来了——这是"改造完项目反而坏了"的最常见原因。
- **合成样例要真合成**：真实数据的替代品必须是编造的，不能用脱敏后的真数据（手机号打码、姓名缩写仍属个人信息）。
- **改完复扫**：`Scanner.ps1 -Mode secrets` 再跑一次，确认没有残留。

### 第 5 步：git 历史处置

先回答"这些值进过历史吗、推过远端吗"，再决定做不做重写。判断依据：

```bash
git log -S "<被泄露的值>" --oneline    # 该值是否出现在历史提交里
git remote -v                          # 有没有远端
git log origin/<branch> --oneline | head   # 是否已经推送
```

处置顺序**不能颠倒**：

1. **先轮换密钥**。历史重写能让公开仓库变干净，但挡不住已经抓取过的人。轮换才是真正的止损，重写只是减少继续暴露的面。
2. 判断值是否进过历史、是否推过远端。
3. 如果进过且推过，向用户说明重写历史的代价——所有协作者必须重新克隆，已有 fork 与 PR 会错乱，已打标签需手动处理——再由用户决定是否重写。
4. 用户同意后，按 `references/secret-patterns.md` 里的 `git filter-repo` 方案执行；未安装该工具时先给出安装命令，不要擅自 `pip install`。

尚未推送到任何远端的仓库是最幸运的情况：直接重写历史没有代价，越早处理越好。

### 第 6 步：开源改造

按顺序补齐，每份文件生成前确认一次。**不要一次丢出十几个文件**，用户无法逐份审阅，等于变相绕过确认。

**核心四件套（必须）**

- `README.md`：一句话说清项目是什么、给谁用；安装、运行、测试命令必须是从本仓库实际跑通的；截图用占位路径而不是虚构链接。**已有 README 时不要直接重写**——先跑 `-Mode readme` 拿客观问题清单，再从"第一句话 + 快速开始"开始逐项优化，每改完一步让用户看一眼。设计规则见 `./references/readme-design.md`。
- `LICENSE`：默认 MIT，年与版权人按用户信息填；换 Apache-2.0 或 GPL 前先问，许可证不可随意更改。**README 里必须有许可证章节并与 LICENSE 文件一致**——只有文件没有声明，读者不知道能不能用
- `.gitignore`：按语言从 `./assets/gitignore-templates/` 取模板，并确保至少覆盖 `.env*`、`*.pem|*.key|*.p12|*.pfx`、依赖目录、构建产物、IDE 配置
- `.gitattributes`：统一换行符，避免 Windows 用户提交后整个仓库显示为改动；二进制文件标记为 binary

**协作文件（推荐）**

- `CONTRIBUTING.md`：怎么装环境、怎么跑测试、提交信息规范、PR 流程
- `CODE_OF_CONDUCT.md`：采用 Contributor Covenant，需填入联系方式——**先确认用户愿意公开哪个邮箱**
- `.github/ISSUE_TEMPLATE/`（bug 报告与功能请求）、`.github/PULL_REQUEST_TEMPLATE.md`

**CI 与元信息（按需）**

- `.github/workflows/ci.yml`：按语言选模板，跑 lint 与测试；**不要把任何密钥写进 workflow**，用 `${{ secrets.* }}`
- `CHANGELOG.md`：采用 Keep a Changelog 结构，首条为 `Unreleased`
- 仓库元信息：`description`、`topics`、社交预览图建议，做成一段可直接复制的内容交给用户

**提交历史整理**（可选、破坏性）

合并琐碎提交、规范 commit message 能让公开历史更可信，但它等价于重写历史。执行前必须提醒：这一步会让已有 fork 和 PR 失效。若仓库尚未推送，代价为零；已推送则优先建议用 squash 合并的方式在下次大版本时处理，而不是中途重写。

**创建远端（使用 gh CLI）**

`gh` 已安装时可以用一条命令建仓库并推送，但**公开/私有必须由用户当场确认**：

```bash
gh repo create <name> --public --source . --remote origin --push \
  --description "<描述>"
gh repo edit --add-topic <topic1> --add-topic <topic2>
```

建仓前先确认三件事：仓库名、可见性（`--public` 或 `--private`）、是否要立即 push。先创建为 `--private`、确认页面内容无误后再转为 public，是更稳妥的路径——很多问题只有在 GitHub 的渲染视图里才看得出来。

### 第 7 步：交付前终检

逐项确认后才算完成：

- [ ] 复扫 `-Mode secrets` 与 `-Mode pii` 均无新增
- [ ] P0 清单里的每个密钥都已轮换，而不只是从文件里删掉
- [ ] 跑 `-Mode readme`：无死链、无未替换占位符、许可证声明与 LICENSE 一致
- [ ] 从零克隆一份到临时目录，按 README 的步骤能跑起来
- [ ] README 提到的配置文件、脚本、命令都还存在（文档漂移检查）
- [ ] 仓库根目录没有残留的临时脚本、个人笔记、`report.json` 之类的扫描产物
- [ ] `git log` 的作者姓名与邮箱是用户愿意公开的
- [ ] 仓库页面的 description 与 topics 已设置

## 边界

用户可能会因为"扫描器没报警"而认为项目可以安全公开。这个结论不成立，需要明确纠正：正则和熵值只能识别**有固定形态的**敏感信息，而"这个价格表是公司未公开的""这张截图里是我们客户的名字"只有人知道。技能的职责是把可机械判定的部分查干净，并对无法机械判定的部分提出明确的问题。

同样，用户说"直接帮我传上去"时不要跳过确认。公开是不可逆动作，值得多问一句。
